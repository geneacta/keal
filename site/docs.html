The memory model

Compiling to native code makes one question unavoidable which an interpreter can dodge — what a value is in bytes, and who frees it. The short version: reference counting. Every heap object carries its count. No collector, no ownership annotations, no borrow checker.

Fields keep declaration order, padding and all — a struct whose shape the author cannot predict is one that cannot be handed to C. keal layout prints the whole table for any program, so none of it has to be taken on trust:

$ keal layout point.keal ⧉ copy 
record Point
  24 bytes, align 8, 0 of which is padding
  offset  size  field                as
       0     8  <reference count>    usize
       8     8  x: Float             f64
      16     8  y: Float             f64

Nullable niches

T? is free where a spare bit pattern exists — and says so where it is not:

TYPESIZEWHY
String?= Stringthe null pointer is the niche
Int?2 × Intevery bit pattern is a valid Int — a tag is added, and priced openly
✦

The layouts of a sample program are snapshotted in the test suite — changing a representation shows up as a diff, not as a surprise.

Cycles — the open question

Reference counting leaks cycles; that is its one honest weakness. The three candidate answers — a documented leak, weak references, a cycle collector — are weighed in docs/memory.md and not yet chosen. Until one is, a cyclic value never dies — and never runs its deinit.
